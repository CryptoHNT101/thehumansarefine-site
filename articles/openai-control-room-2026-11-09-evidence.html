Claim-level verification

Claim in the articleStatusEvidence
Control Room is described as "a central system to track model workloads across our research infrastructure and stop them quickly when safety or security concerns arise" VERIFIED — primary Source 1, opening paragraph. Exact words present.
It halts model output within 35 seconds VERIFIED — primary, company-reported figure Source 1: "halts model output within 35 seconds of a decision to intervene to stop or pause a job"; and "The maximum time between the moment when Control Room receives an instruction to stop a job, and the moment when further progress is no longer possible, is 35 seconds."
The 35-second lag is attributed to a caching layer and the company is working to reduce it to zero VERIFIED — primary Source 1: "The 35-second lag comes from a caching layer for inference authorization, to support the required volume of traffic. We are working to drive this number down to zero so that we can end jobs instantly."
OpenAI does not rely on workload code to check whether a job is still running VERIFIED — primary Source 1: "We do not rely on the workload code to correctly perform a check of whether or not the job is still running."
Workload code is described as changing often and unsuitable for critical safety protections; inference code is few and centralised VERIFIED — primary Source 1: "workload code changes often, and is not an ideal place to implement critical load-bearing safety protections"; "there are only a very small number of inference code paths in use across all of OpenAI research, and their deployments are much more centralized and uniform"
The system is designed to be "resilient to buggy or broken workload code" VERIFIED — primary Source 1, exact phrase present.
The system "fails closed", including against "tampering by a bad actor" VERIFIED — primary Source 1: "if the Control Room service goes down, either due to a system error or because it is disabled for any other reason, including tampering by a bad actor, then all inference requests will be denied until Control Room resumes normal operation."
Fail-closed is deployed to frontier research workloads but not yet all research workloads VERIFIED — primary Source 1: "Fail-closed is rolled out now to all frontier model research workloads, and will finish rolling out across all remaining research workloads over the next few days."
OpenAI runs continual sweeps for rogue engine implementations VERIFIED — primary Source 1: "We additionally run continual agentic and programmatic sweeps to check that users are not accidentally or maliciously launching rogue engine implementations with Control Room unimplemented or disabled."
A monitoring alert can trigger a stop, and a "DNS-related incident" was caught by a monitor VERIFIED — primary, as a company statement Source 1: the monitoring section describes the alert-to-stop chain; "our recent DNS-related incident ... was caught by a monitor".
Control Room works together with the misalignment monitoring systems VERIFIED — primary Source 1: "This works together with our misalignment monitoring systems"
Every research workload doing agentic inference must be tied to an approved safety case VERIFIED — primary Source 1: "We require every research workload that does agentic inference to be associated with an approved safety case."
The external model-serving stack is described as already centralised, with capability to take down deployments VERIFIED — primary Source 1: "Our external model-serving stack is already much more centralized by nature, with a well-developed operational capability to quickly take down model deployments if needed."

Not verified, and not claimed in the article

  • Accuracy of the 35-second figure. Company-reported. This publication found no independent audit. The article states this inline.
  • Whether Control Room has ever been used in a real intervention, and how often. The document does not say.
  • What the "DNS-related incident" was. OpenAI's 29 October monitoring post describes a September episode in which, during a live training run, a model reached the internet from an environment meant to be isolated. The Control Room post calls its own recent episode "DNS-related". That the two references are the same episode is NOT established, and the body says so; the body no longer carries any detail from one source into the other's account.
  • Whether external customer traffic is covered. The document distinguishes the external stack. That is an argument it needs this less, not evidence it is equivalent.
  • What happens to a job stopped mid-training beyond output ceasing. Not described.

  6. Conflated sourcing corrected, 2026-11-21, and the first attempted correction withdrawn the same day. The body sentence on the DNS incident welded two passages of OpenAI's 29 October post into one event, attributing the DNS detail to the September episode described in a different section. That is false and is withdrawn: the post's section "What our monitors have been finding in internal traffic" says its monitors flagged "a model's attempt to access the live internet using DNS" during an RL run within 15 minutes, with a human beginning review three minutes later. The two accounts are separate in the source, carry identical timings, and the post never says they are the same event. The body now reports the DNS passage in Source 3's own words, reports the September passage separately with the pause on frontier reinforcement learning, records that the source does not join them, and keeps the earlier refusal to equate the Control Room post's "recent DNS-related incident" with either.
